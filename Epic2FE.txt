Epic 2 Frontend Backlog
HomeHealthCare

Purpose

This document converts Epic 2 from `Requirements.txt` into a frontend delivery backlog for the web application.

Epic 2 title

Agency setup and configuration

Epic 2 feature scope from the requirements

- agency profile
- service lines
- visit types
- caregiver skills/certifications
- task templates
- documentation templates
- branch policies
- alert rules
- mileage/pay settings

Planning assumptions

- Epic 1 frontend and backend are complete
- Epic 2 is primarily an admin web experience
- Epic 2 frontend depends on new public backend APIs for every module
- Epic 2 should reuse Epic 1 shell, access control, audit patterns, and form handling patterns

Status legend

- BLOCKED: frontend should wait for the corresponding Epic 2 backend APIs

FE2-01 — Agency setup navigation and information architecture
Related Epic 2 features: all
Backend status: BLOCKED

Story
As an agency admin, I want a coherent setup area in the web app so configuration modules are easy to find and manage.

Frontend acceptance criteria

- a dedicated Epic 2 setup/configuration section exists in navigation
- routes are grouped by configuration domain
- role-based navigation visibility follows backend permissions
- unauthorized deep links render controlled `403` states
- setup modules share consistent page and table patterns

Definition of done for Epic 2 frontend

Epic 2 frontend is done only when:

- every Epic 2 configuration module is reachable from the app shell
- setup modules use backend APIs rather than local-only placeholder state
- create/edit/deactivate flows are usable and permission-aware
- conflict and dependency errors are shown clearly
- owner-only and admin-only restrictions are visible and consistent
- core Epic 2 screens are regression-covered
