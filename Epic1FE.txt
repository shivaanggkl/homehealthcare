Epic 1 Frontend Backlog
HomeHealthCare

Purpose

This document translates Epic 1 backend work into the frontend stories required to deliver Epic 1 on the web application.

It is based on:

- the Epic 1 requirements in `Requirements.txt`
- the current backend code and public HTTP API surface in `README.md`
- the backend stories you marked complete:
  - `S01–S11`
  - `S12–S14`
  - `S16`
  - `S18–S25`
  - `S24–S25`
  - `S27–S28`
  - `S30–S39`
  - `S44–S48`

Important planning note

Epic 1 backend is stronger than the current REST API surface.

What is already exposed as public backend APIs:

- login, logout, refresh
- forgot/reset/change password
- MFA enrollment and MFA login challenge
- session status and active-session revocation
- agency MFA policy
- admin notification preferences
- password policy

What exists mostly in backend services but is not yet exposed as public REST APIs:

- invite user
- accept invite
- user directory
- edit user profile, role, and branch assignments
- self-service profile update
- audit log viewer
- agency settings
- branch management
- security settings beyond MFA policy

Status legend

- READY: frontend can be built now against existing backend APIs
- PARTIAL: some backend support exists, but additional API work is needed
- BLOCKED: service/domain logic exists or requirements exist, but frontend should wait for public APIs

FE-01 — App shell, auth bootstrap, and session-aware startup
Related Epic 1 stories: `E1-S18`, `E1-S19`, `E1-S32`, `E1-S33`, `E1-S34`
Backend status: READY

Story
As a signed-in user, I want the frontend to restore my authenticated state correctly so I can continue working without manual re-login on every refresh.

Frontend acceptance criteria

- app boot checks current auth state using `GET /api/auth/session`
- authenticated state can be restored from secure cookies or token/session headers for local dev
- expired or revoked sessions send user back to login cleanly
- session metadata is stored in frontend auth state only as needed for UX
- logout fully clears local auth state

========================================================================
FE-02 — Email/password login screen
Related Epic 1 stories: `E1-S18`, `E1-S23`
Backend status: READY

Story
As a user, I want a clean login screen so I can sign in with email and password.

Frontend acceptance criteria

- email/password form posts to `POST /api/auth/login`
- generic invalid-credentials error is shown without account leakage
- rate-limit and temporary-lockout responses are handled clearly
- successful login routes user either to app home or MFA challenge depending on response
- access token, refresh token, and session id from response are supported for local non-cookie dev flows

FE-03 — MFA login challenge screen
Related Epic 1 stories: `E1-S25`
Backend status: READY

Story
As a protected user, I want to complete MFA after password verification so login remains secure.

Frontend acceptance criteria

- challenge screen is shown when login returns `mfaRequired=true`
- user can submit either TOTP code or recovery code to `POST /api/auth/login/mfa`
- used recovery-code success state is communicated clearly
- expired or invalid challenge errors are handled cleanly
- successful challenge completes auth bootstrap and redirects into the app

FE-08 — MFA status and enrollment settings
Related Epic 1 stories: `E1-S24`
Backend status: READY

Story

Frontend acceptance criteria

Related Epic 1 stories: `E1-S33`

Related Epic 1 stories: `E1-S29`, `E1-S27`, `E1-S28`, `E1-S31`
Backend status: PARTIAL

Story
As the UI, I want permission-aware routing and menus so users only see what they should use.

Frontend acceptance criteria

- menu items and routes can be hidden or disabled by role and permission
- unauthorized deep links render a controlled unauthorized state
- role-based default landing pages are supported
- branch-limited and agency-wide roles can be represented in frontend permission metadata
- backend `403` and `404` security responses are handled gracefully

Dependency note

Backend authorization exists, but a frontend-facing "current user / current permissions / current agency context" endpoint is still needed for a robust implementation.

Definition of done for Epic 1 frontend

Epic 1 frontend is meaningfully complete when:

- all READY stories are implemented end to end
- PARTIAL stories are either implemented or explicitly deferred
- backend gaps for BLOCKED stories are converted into API backlog items
- auth, MFA, session, and permission UX paths are tested in browser flows
- unauthorized, expired-token, expired-link, and timeout states all have controlled UI
