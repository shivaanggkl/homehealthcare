Epic 7 Frontend Backlog
HomeHealthCare

Purpose

This document converts Epic 7 from `Requirements.txt` into a frontend delivery backlog for EVV and visit-exception workflows.

Epic 7 title

Visit execution and EVV

Epic 7 feature scope from the requirements

- clock-in / clock-out
- GPS + timestamp verification
- device metadata
- geofence tolerance rules
- patient/caregiver signature
- missed-visit workflow
- exception reason capture
- supervisor notification
- order/escalation creation on exceptions

Planning assumptions

- Epic 1 frontend and backend are complete and provide auth, session, RBAC, protected-route, and audit-view patterns
- Epic 5 scheduling workflows are complete and provide visit context and assignment state
- Epic 6 frontend and backend are complete and provide the caregiver mobile shell, visit detail, execution basics, offline sync patterns, signature upload, and field artifacts
- Epic 7 frontend extends the caregiver mobile execution experience with compliance-sensitive EVV proof and exception handling
- Epic 7 may also require limited admin or coordinator-facing review surfaces, but it should stop short of the broader QA workspace that belongs to Epic 10
- Epic 7 should remain focused on proof-of-visit and exception routing, not general note-template/form work from Epic 8 or generalized messaging expansion from Epic 9
- mobile EVV flows should stay caregiver-friendly while still making warning, blocking, and exception states explicit
- privacy-sensitive patient and device data should be minimized in the UI and never expose internal-only metadata unnecessarily

Status legend

- BLOCKED: frontend should wait for the corresponding Epic 7 backend APIs

FE7-01 — EVV navigation and caregiver information architecture
Related Epic 7 features: all
Backend status: BLOCKED

Story
As a caregiver, I want EVV actions and exception workflows to fit naturally into the mobile visit flow so proof-of-visit work is easy to complete correctly.

Frontend acceptance criteria

- EVV actions are reachable from the mobile visit workflow
- caregiver-facing routes distinguish:
  - normal visit execution
  - EVV verification
  - missed-visit reporting
  - exception follow-up
- unsupported or unauthorized EVV routes render controlled states
- EVV status is visible without overwhelming the caregiver with admin detail

Definition of done for Epic 7 frontend

Epic 7 frontend is done only when:

- EVV and missed-visit workflows are reachable through coherent caregiver mobile routes
- clock-in, clock-out, missed-visit, exception, and signature-completion states use real backend APIs rather than placeholder local state
- GPS/time/geofence outcomes are shown clearly with understandable warning vs blocking states
- caregivers can tell when visit verification is complete, incomplete, warning-only, or blocked
- supervisor notification and escalation outcomes are reflected clearly in the UI where supported
- privacy-sensitive patient and device information is minimized appropriately
- coordinator or reviewer EVV issue visibility exists for authorized users
- core Epic 7 screens are mobile-safe and regression-covered
