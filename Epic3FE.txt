Epic 3 Frontend Backlog
HomeHealthCare

Purpose

This document converts Epic 3 from `Requirements.txt` into a frontend delivery backlog for the web application.

Epic 3 title

Patient / client management

Epic 3 feature scope from the requirements

- patient demographics
- contacts and emergency contacts
- address and geo-location
- service eligibility
- diagnoses / conditions
- payer linkage
- allergies / medications later phase
- episode / service authorization tracking
- document attachments

Planning assumptions

- Epic 1 frontend and backend are complete
- Epic 2 setup data is available and reusable where Epic 3 screens need service lines, visit types, or branch context
- Epic 3 is primarily an admin and coordinator web experience in this phase
- patient attachments are managed through secure backend APIs, not direct unaudited storage access
- allergies and medications are intentionally later-phase and are out of scope for this Epic 3 frontend backlog

Status legend

- BLOCKED: frontend should wait for the corresponding Epic 3 backend APIs

Related Epic 3 features: all

Definition of done for Epic 3 frontend

Epic 3 frontend is done only when:

- patient/client records are reachable from the app shell through a dedicated patient workspace
- Epic 3 screens use backend APIs rather than placeholder local state
- create/edit flows for demographics, contacts, address, eligibility, diagnoses, payer links, authorizations, and attachments are usable and permission-aware
- conflict, validation, and unauthorized errors are shown clearly
- patient detail navigation is coherent and reusable
- attachment UX is secure and controlled
- core Epic 3 screens are regression-covered
