Epic 6 Backend Backlog
HomeHealthCare

Purpose

This document converts Epic 6 from `Requirements.txt` into a backend delivery backlog.

Epic 6 title

Caregiver mobile app

Epic 6 feature scope from the requirements

- secure login
- today’s visits
- route/order of visits
- patient summary
- care instructions
- start visit / end visit
- GPS proof
- offline-first support
- signature capture
- task checklist
- quick notes
- photo uploads
- incident flagging
- message center

Planning assumptions

- Epic 1 is complete and provides auth, session management, RBAC, tenancy, audit, and branch-aware authorization
- Epic 2 is complete and provides agency configuration, visit types, service lines, alert rules, documentation templates, and setup catalogs
- Epic 3 is complete and provides patient records, contacts, address, diagnoses, payer/authorization context, and patient attachment patterns
- Epic 4 is complete and provides caregiver profiles, skills, credentials, geography, availability, and workforce context
- Epic 5 is complete and provides visit, assignment, recurrence, conflict, reschedule, cancellation, and scheduling board APIs
- Epic 6 is the caregiver-facing mobile execution layer, not the full compliance-grade EVV exception and missed-visit workflow from Epic 7
- Epic 6 should produce durable visit-session and field-documentation records, not UI-only state
- mobile execution must tolerate intermittent connectivity through sync-safe request and event models
- secure mobile APIs should minimize data needed for field execution and avoid exposing admin-only scheduling internals

Scope rule

- Include only Epic 6 backend work
- Cover mobile session contracts, visit-execution state, offline sync support, field notes/tasks/photos/signatures/incidents/messaging APIs, authorization, audit, and tests
- Do not include frontend-only tasks
- Do not pull full EVV compliance workflows, geofence tolerance policy engines, missed-visit escalation trees, or revenue-readiness review queues from later epics into Epic 6

BE6-01 — Define caregiver mobile execution architecture and lifecycle rules
Related Epic 6 features: all
Current status: NOT STARTED

Story
As the platform architect, I need a coherent mobile execution domain so caregiver-facing visit work follows consistent state, ownership, and audit rules.

Recommended acceptance criteria

- Epic 6 domain entities are defined explicitly, including:
  - mobile device session context
  - caregiver mobile inbox or today-work query model
  - mobile visit execution session
  - route stop/order projection
  - care-instruction snapshot
  - mobile task completion state
  - quick note entry
  - field photo attachment
  - field signature artifact
  - incident report
  - mobile message thread summary
  - offline sync envelope
- visit-execution lifecycle states are defined for at least:
  - not_started
  - in_progress
  - paused optional
  - completed
  - failed_sync optional
- ownership expectations are documented for caregiver, visit, branch, patient, and assignment linkage
- extension points for Epic 7 EVV and missed-visit exception flows are documented without implementing those later-epic behaviors fully
- audit expectations are documented for all mobile execution mutations

BE6-02 — Create caregiver mobile home / today-work query model
Related Epic 6 features: today’s visits, route/order of visits
Current status: NOT STARTED

Story
As a caregiver using the mobile app, I need a backend today-work query so I can see the right visits in the right operational order.

Recommended acceptance criteria

- a mobile today-work query model exists
- the query returns today’s assigned visits for the authenticated caregiver
- each item includes enough context for the mobile app, including:
  - visit id
  - patient display summary
  - branch optional
  - planned start and end
  - timezone
  - schedule status
  - route order if available
  - current mobile execution status if any
- day filtering behavior is explicit and timezone-aware
- only the caregiver’s authorized assigned work is returned
- the query is test-covered

Definition of done for Epic 6 backend

Epic 6 backend is done only when:

- caregiver mobile work is exposed through secure, caregiver-scoped APIs
- mobile today-work, visit execution, patient summary, task checklist, note, photo, signature, incident, and messaging contracts exist with clear lifecycle rules
- offline-tolerant and idempotent mutation handling exists for representative field actions
- start/end visit actions support location-proof inputs without overreaching into later Epic 7 compliance logic
- tenant isolation and self-context authorization are enforced for all mobile execution APIs
- audit events exist for key field mutations
- core Epic 6 mobile flows are regression-covered
