Epic 15 Frontend Backlog
HomeHealthCare

Purpose

This document converts Epic 15 from `Requirements.txt` into a frontend delivery backlog for dashboard and analytics.

Epic 15 title

Dashboard and analytics

Epic 15 feature scope from the requirements

- today’s visits
- unfilled visits
- late starts
- missed visits
- documentation aging
- QA backlog
- caregiver utilization
- branch performance
- revenue readiness count
- compliance exceptions

Planning assumptions

- Epic 1 frontend and backend are complete and provide auth, session, RBAC, protected-route, and audit-view patterns
- Epics 3 through 14 are complete enough to provide the source operational domains that Epic 15 summarizes instead of redefining
- Epic 5 provides the scheduling and visit context used for visit-load, unfilled, and late-start analytics
- Epic 7 provides missed-visit and related EVV exception context
- Epic 8 provides documentation status and age context
- Epic 10 provides QA backlog context
- Epic 11 provides compliance-exception context
- Epic 14 provides revenue-readiness context
- Epic 15 frontend should support command-center visibility and drilldown, not re-implement the underlying operational mutation workflows already owned by earlier epics
- analytics screens should stay privacy-aware and show only the minimum patient, caregiver, payer, and branch detail needed for operational leadership use

Status legend

- BLOCKED: frontend should wait for the corresponding Epic 15 backend APIs

FE15-01 — Analytics workspace information architecture and route model
Related Epic 15 features: all
Backend status: BLOCKED

Story
As an owner, admin, or operations lead, I want dashboard and analytics routes to fit naturally into the app so command-center visibility and drilldowns are easy to find.

Frontend acceptance criteria

- protected analytics workspace route exists
- dedicated routes exist for:
  - dashboard summary
  - operational drilldown
  - branch performance view
  - caregiver utilization view
  - revenue/compliance summary drilldown
- unsupported or unauthorized Epic 15 routes render controlled states
- analytics routes can link back into relevant source workspaces where authorized

FE15-09 — Shared analytics refresh and filter UX
Related Epic 15 features: all
Backend status: BLOCKED

Story
As the frontend team, I want one refresh and filter pattern for dashboards and drilldowns so Epic 15 behavior stays predictable and easy to scan.

Frontend acceptance criteria

- analytics refresh and filtering use a consistent pending/success/failure pattern
- branch/date/status filters behave consistently across dashboard and drilldowns

- failed refresh actions remain understandable and retryable where practical

Definition of done for Epic 15 frontend

Epic 15 frontend is done only when:

- dashboard, drilldown, branch-performance, utilization, and revenue/compliance summary screens are reachable through coherent protected routes
- summary, drilldown, branch-performance, utilization, and filter/refresh flows use real backend APIs rather than placeholder local state
- operational, backlog, utilization, revenue, and compliance outcomes are shown clearly and consistently
- leadership-facing command-center visibility exists for authorized users
- privacy-sensitive patient, caregiver, payer, and branch context is minimized appropriately
- Epic 15 screens are usable on smaller operational devices
- core Epic 15 screens are regression-covered
