Epic 1 Backend Completion Backlog
HomeHealthCare

Purpose

This document lists only the incomplete backend work still needed to finish Epic 1 properly.

It is based on:

- the Epic 1 requirements in `Requirements.txt`
- the current backend public API surface in `README.md`
- the Epic 1 frontend backlog in `Epic1FE.txt`

Scope rule

- Include only Epic 1 backend gaps
- Focus on missing or partial public backend contracts, not frontend work
- Prefer API/controller completion stories where domain/service logic already exists

Important note

Epic 1 backend already covers a large amount of domain and service logic.
The main remaining gap is that several Epic 1 capabilities are not yet exposed as stable public HTTP APIs for frontend use.

Status legend

- PARTIAL: some backend support exists, but the public contract is incomplete
- MISSING API: domain/service logic exists or requirements exist, but no frontend-consumable public API is available

========================================================================
BE-01 — Current user access profile endpoint
Related Epic 1 stories: `E1-S27`, `E1-S28`, `E1-S29`, `E1-S31`
Current status: PARTIAL

Why this is needed

Frontend route authorization in `FE-12` and role-based home behavior in `FE-25` currently rely on frontend fallback metadata because the backend does not expose a current-user/current-agency/current-permissions contract.

Story
As the frontend and backend together, we need a current access profile endpoint so role, permission, agency, and branch scope are sourced from the backend instead of frontend overrides.

Recommended acceptance criteria

- `GET /api/me/access` or equivalent exists
- response includes:
  - user id
  - current agency id
  - membership id
  - role
  - effective permissions
  - branch scope type
  - assigned branch ids where applicable
- response is tenant-safe and branch-safe
- unauthorized or inactive membership states are handled cleanly
- tests cover agency-wide and branch-limited users

- agency MFA policy API exists

Gap

- no owner-facing configuration API for session security policy
- no consolidated backend contract for the full security settings screen

Story
As the backend, we need a complete security settings contract so the owner-facing Epic 1 security screen is fully backed by real API behavior instead of partial read-only sections.

Recommended acceptance criteria

- current security settings contract is documented and explicit

  - idle timeout policy
  - absolute session duration policy
  - warning window policy
- if session timeout configuration does not belong in Epic 1, document that scope boundary clearly
- tests cover authorization and validation for all editable security settings
