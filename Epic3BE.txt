Epic 3 Backend Backlog
HomeHealthCare

Purpose

This document converts Epic 3 from `Requirements.txt` into a backend delivery backlog.

Epic 3 title

Patient / client management

Epic 3 feature scope from the requirements

- patient demographics
- contacts and emergency contacts
- address and geo-location
- service eligibility
- diagnoses / conditions
- payer linkage
- allergies / medications later phase
- episode / service authorization tracking
- document attachments

Planning assumptions

- Epic 1 is complete and available as the security, tenancy, RBAC, audit, and session foundation
- Epic 2 is complete and provides reusable agency setup data such as service lines, visit types, templates, and branch policies
- Epic 3 data is agency-scoped by default, with branch association supported only where the operating model clearly requires it
- patient records are long-lived business entities and must be audit-sensitive from day one
- attachments require metadata, storage abstraction, and authorization controls, not just file upload
- allergies and medications are explicitly later-phase and should not be treated as MVP scope for Epic 3

Scope rule

- Include only Epic 3 backend work
- Cover domain model, public APIs, validation, authorization, audit, storage contracts, and tests
- Do not include frontend-only tasks

Definition of done for Epic 3 backend

Epic 3 backend is done only when:

- patient/client data is modeled with clear lifecycle and tenancy rules
- every Epic 3 feature area has a public API where the frontend needs one
- RBAC is enforced for patient records, contacts, eligibility, payer links, authorizations, and attachments
- attachment upload and download are secured and auditable
- duplicate, conflict, and invalid-state behavior returns controlled errors
- patient-related audit events are visible through the existing audit surfaces
- automated tests cover CRUD, denial, conflict, and attachment security paths
